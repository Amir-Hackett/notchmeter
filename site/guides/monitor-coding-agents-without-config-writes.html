Monitoring coding agents without letting an app write to your config

Most apps that watch coding agents do it by putting a command into the agent's settings file, and several do it on first launch without asking. That file also holds your permissions, your hooks and your status line. Here is what you can know without anything being written, what a hook adds, and exactly what is written, where, when you decide to add one.

  • Published 24 September 2026
  • Tested on Notchmeter 0.9.0
  • Other apps' READMEs read 2026-09-24

The short answer

Two tiers. With nothing written anywhere, Notchmeter 0.9.0 finds running agent sessions from your own processes and the files the agents already keep, and reads usage from the logins they already saved. That tells you what is running, where and roughly whether it is busy. Knowing the exact moment a turn ends, knowing that an agent is waiting for you, and answering it from the notch need the agent to say so, which is what a hook is. Notchmeter adds one only when you press the button, after a timestamped backup, merged so nothing of yours changes, and removing it is deleting its entries or restoring the backup.

The risk is real enough that AgentNotch's changelog, read the same day, records: "Live Prompts can no longer overwrite your agent's configuration, and every write leaves a backup." Backups and merges are the minimum; asking first is the point.

Tier one: nothing written

Notchmeter 0.9.0 lists sessions before any hook is installed. It reads, and never writes:

  • Your own running processes that have a terminal, to find agent sessions, the folder each runs in and the terminal it runs in. Another user's processes are not looked at, a process's environment is never read, and a headless run with no terminal is not listed.
  • Claude Code's ~/.claude/sessions folder. Claude Code documents that it "holds one small file per running session, used to detect concurrent sessions and crashes". It does not document what is in those files, so Notchmeter reads only the fields it needs, treats every one as optional, and never opens the key file that sits beside each.
  • The end of that session's transcript, for its model and branch, and its title only while Show what a session is working on is on.

Whether a session is working is a guess from what those show. For Claude Code its own session file says busy or idle; for the others it is how much processor time the process is using, since a terminal agent spends it while it streams and draws its spinner and not while it sits at a prompt. That is enough to show what is running, in which project, and roughly whether it is busy. It is not enough to know three things, and Notchmeter does not pretend otherwise:

  • When a turn ends. The guess trails the turn by a few seconds. agent-notch, which also works without hooks, puts it plainly: "only the agent knows when its turn ends."
  • That an agent is waiting for you. No process signal proves it, so a detected session never claims to be waiting: through a permission prompt its row still says working.
  • Answering. There is no channel back to the agent without a hook.

A session found this way carries a detected mark, the way every usage figure is labelled with its source, and the card carries one line, Install the hook for exact turn ends and answering from the notch, with a button that opens the hook's row in Settings. Nothing is written until you choose Add there.

The usage meters were always in this tier. Each reads the login its tool already saved on the Mac, makes the read-only status request that tool's own app makes, and never refreshes, stores or forwards a token.

Tier two: the hook, on your click

A hook is the agent telling Notchmeter what happened, the moment it happens: a turn started, a turn ended, a permission is waiting, a question has options. That is what makes the waiting dot, the finished tick, the news in the notch and answering from the notch possible. Here is exactly how it is written.

  1. Only when you press it. Settings › Integrations › Hooks has a row per assistant with Add, and Show snippet… if you would rather paste it yourself. The first launch offers the Claude Code hook once, as a button. No hook is ever installed without that click.
  2. A backup first, beside the file: settings.json.bak-yyyyMMdd-HHmmss (or hooks.json.bak-…).
  3. A merge, not a rewrite. Notchmeter's entry is appended under each event that lacks one. Hooks already there, their matchers and their order are kept, and so are the file's permissions. Nothing is written when every event already has the entry. A file that is not a JSON object is left untouched, and the button says why.

The one write that is not a click

If you move the app, a hook you installed points at the old path and goes quiet; if you update to a version that listens for more events, the entry you installed is out of date. So by default the app repairs its own entries at launch: after the same backup, it points them at the running copy and adds an entry for any event the current version listens for, leaves every other hook untouched, and never does it from a copy running out of a build folder. It never adds a hook for an assistant you have not installed one for. If you want no write at all after the one you pressed, turn off Repair a hook that points at an old copy at launch in Settings › Integrations › Hooks, and use the row's Repair button when you choose to.

The status line and the plugin

Install status line… sets Claude Code's statusLine after the same backup. A status line you already had is kept: Notchmeter runs yours with the same input and passes its output through, so Claude Code's bar still shows your line. The Claude Code plugin installs no hook and no status line; those stay a button in Settings.

What the hook sends

The event's name, the session id, the project folder's name, the branch and the permission mode; the first line of a prompt, which the app drops on arrival unless Show what a session is working on is on; and for a permission, the tool's name and a bounded summary, never the raw input. It goes over a Unix socket on the Mac that accepts a connection only from a copy of Notchmeter whose code signature matches, and it fails open: with the app not running, or anything wrong, the agent carries on as if no hook existed. docs/hooks.md lists every field for every assistant.

Undoing it

  • Claude Code: delete the groups whose command contains Notchmeter … --hook from ~/.claude/settings.json, and the statusLine entry, restoring your own if Notchmeter chained it; or restore the .bak copy.
  • Codex, Cursor, Gemini CLI: delete the entries whose command contains --hook --tool codex, --tool cursor or --tool antigravity, or restore the backup.
  • Copilot CLI: delete ~/.copilot/hooks/notchmeter.json and restart Copilot.

Switching an assistant off in Notchmeter, or quitting it, also stops its hook having any effect; the command still runs and exits at once.

Choosing

If you want to know what is running and what it is costing, tier one is enough and nothing is written. If you want to know the moment an agent needs you, and to answer it without finding the terminal, add the hook for that one assistant. You can start with the first and add the second later, one assistant at a time, and take it out again whenever you like.
