# Privacy and terms

The whole of what Notchmeter reads, where it sends it, what it keeps, how often it asks and how it reads each vendor's terms. The [README](../README.md#privacy-and-terms) has the summary; the per-provider table of endpoints and identities is in [accuracy.md](accuracy.md#who-each-request-says-it-is).

Notchmeter is a read-only instrument. In plain terms:

**What it reads.**

- Claude Code's saved login: the Keychain item `Claude Code-credentials` (asked with prompts off, then through `/usr/bin/security find-generic-password`), or `$CLAUDE_CONFIG_DIR/.credentials.json` / `~/.claude/.credentials.json` when the Keychain has no such item, or `CLAUDE_CODE_OAUTH_TOKEN`. The access token, its expiry and the plan name are taken from it. Whether `ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROOK`-style variables or an `apiKeyHelper` are set is read as a yes/no, to say that an API-key setup has no plan window.
- Codex's saved login: the access token, account id and expiry in `auth.json` under `$CODEX_HOME`, `~/.config/codex` or `~/.codex`.
- Cursor's saved login: the `cursorAuth/accessToken` row of `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`. The database is copied to a private temporary file for the read and deleted straight after, so the editor's live database is never opened.
- Gemini CLI's saved Google login: the access token and its expiry in `~/.gemini/oauth_creds.json`.
- GitHub Copilot's saved token: `oauth_token` in `~/.config/github-copilot/apps.json` or `hosts.json`, or `gh`'s `~/.config/gh/hosts.yml`.
- Local transcripts, for the cost card and the offline fallback: the `usage` lines of `~/.claude/projects/**/*.jsonl` (also `$CLAUDE_CONFIG_DIR`, `~/.config/claude`, Claude Desktop's `~/Library/Application Support/Claude/local-agent-mode-sessions` when present, and any folder you add under *Also read transcripts from*; only files touched in the last 30 days), the line's `cwd` reduced to the name of the repository it is in (a git worktree folds onto the repository it was cut from, [docs/accuracy.md](accuracy.md)) or, outside one, its last path component, for the per-project split, and the newest `rate_limits` lines in `~/.codex/sessions/**/*.jsonl`.
- Claude Code's `modelPricing` table in `~/.claude/settings.json`, when one is set, so the estimate matches Claude Code's own figure.
- Modification times only, for the polling schedule: of files under the most recently changed `projects` folders of each transcript root, of `~/.codex/sessions/<today>` and `<yesterday>`, of Cursor's `state.vscdb`, of `~/.gemini/oauth_creds.json` and the entries of `~/.gemini/tmp`, `~/.gemini/antigravity` and `~/.gemini/antigravity-cli/conversations`, and of `~/.config/github-copilot`. Contents are not read for this.
- If you install the [Claude Code hook](hooks.md), Claude Code hands `Notchmeter --hook` each event's JSON; the command keeps only the event name, whether Claude is waiting for you, the session id, the folder name of the working directory (or of the repository, when it is a git worktree), the branch named by its `.git/HEAD`, the permission mode, a subagent's id and a stop failure's kind, and passes those to the running app. Three things joined them in 0.7.0, each bounded before it leaves the command and each listed field by field in [docs/hooks.md](hooks.md#what-the-hook-sends): the first line of a prompt (at most 96 characters) as the session's title, which the app drops before it is held anywhere when *Show what a session is working on* (Settings › Assistants › Sessions) is off; on a permission request or a question, the tool's name and a one-line summary of what it wants with a 4 KB excerpt at most (a shell command, an edit's old and new lines, a file's first forty lines; an MCP tool's name alone), or the question and its options, so you can answer from the notch — the raw tool input never leaves the command; and where the hook's own terminal is (the terminal app, its tab or pane id, the controlling tty, tmux and kitty ids), read from the hook process's environment and process ancestry, never from a window or a title, so a click on a session can take you back to it. Each of the three has its own switch there; each assistant's own page in Settings can also switch off *Read its sessions*, after which the app keeps nothing of that assistant's hook events but the fact that one arrived, to refresh its meter (the sessions already held are dropped at the switch), and *Answer from the notch* for that assistant alone. None of it reaches the log, the oracle, the report file, the local API, `--json` or MCP. After 0.7.9 a fourth joined them: when Claude Code updates its task list (the `TaskCreate` and `TaskUpdate` tools, or `TodoWrite` on older builds), the task's id and status and the first line of its subject, or for `TodoWrite` each item's status and the first line of its text (at most 96 characters, at most 50 items), for the Sessions card's checklist; a subagent's task calls are not shown on its session's row; the text is held under the same *Show what a session is working on* switch as the title and dropped on arrival when it is off, and the oracle hears only the counts ([docs/hooks.md](hooks.md#the-task-list)). If you install the [Codex hook](hooks.md#codex), Codex hands `Notchmeter --hook --tool codex` its event the same way, and the command keeps only the event name, the session id, the folder name of the working directory (or of the repository, when it is a git worktree), its branch, the permission mode, a subagent's id, a prompt's first line and, on an approval, the tool's name and the summary just described; never the transcript path, the model, the rest of the prompt or the raw tool input. If you install the [Cursor hook](hooks.md#cursor), Cursor hands `Notchmeter --hook --tool cursor` the same way, and the command keeps only the event name, the conversation id, the folder name of the workspace root (or of the repository, when it is a git worktree), the branch named by its `.git/HEAD`, a stop's status, a subagent's id and a prompt's first line; never the rest of the prompt, the attachments, the transcript path, your email or the model. If you install the [Gemini CLI hook](hooks.md#gemini-cli), the command keeps only the event name, the session id, the folder name of the working directory (or of the repository, when it is a git worktree), its branch, the notification type and a prompt's first line; never the rest of the prompt, the response, the transcript path or the alert's text. If you install the [Copilot CLI hook](hooks.md#github-copilot-cli), the command keeps only the event name, the session id, the folder name of the working directory (or of the repository, when it is a git worktree), its branch, the notification type, a prompt's first line and, on a permission request, the tool's name and summary; never the rest of the prompt, the response, the transcript path, the agent's name or the notification's text. Nothing else is read from any of them; to find the repository, the command stats `.git` in the working directory and its parents and reads a `.git` file's first line ([docs/hooks.md](hooks.md#what-the-hook-sends)). The status line command keeps the context window's fill and size (with its fresh-input, cache-write and cache-read counts), the rate-limit windows, the session cost, the model name and effort level, the session id, the folder name, the git branch and pull-request URL when Claude Code sends them, and since 0.7.0 Claude Code's `prompt_cache` figures (counts, tokens, the causes it names), fast mode, extended thinking, the agent's name, the session's name (the one you set with `--name` or `/rename`, or Claude Code's own title; kept on the session in the app and written to no log, report or notification), the lines added and removed, the time spent waiting on the API and the repository's host, owner and name, and nothing else of the payload.
- Whether the screen is being captured (a yes/no from the window server), only while *Hide usage while the screen is shared* is on.


**Accessibility, only for Auto.** *Readouts › Auto* (Settings, or the Options menu) keeps the readouts clear of the frontmost app's menu titles, and it is the one thing in Notchmeter that uses the Accessibility API. It reads the geometry of that app's menu bar and of the titles in it — where they sit and how wide they are — and nothing else: never a title, a value, a menu's contents, nor any element outside the menu bar, and it never writes anything or performs an action anywhere. It measures when an app comes to the front, remembers the answer per app, and never polls. Auto is off unless you pick it, and picking it is what asks for the permission, and a launch that finds Auto chosen but the permission never granted asks once more per signed copy, while a launch that finds a grant no longer applying (the switch in Privacy & Security on, this copy refused) offers the app's own repair — clear the entry and restart — on the same once-per-copy terms instead of the prompt. No other part of the app asks for Accessibility, nothing is measured while another side is chosen, and a copy that has never picked Auto is never asked at launch. Without the permission (or if you revoke it) Auto stays centred on the notch with every readout, which is where it sits whenever the menu bar leaves room anyway. `--menu-bar` prints the whole of what it read — every menu bar extra any app vends, and which of them it counts — for when the strip ends up somewhere surprising; run it through `open`, since a binary started from a shell is attributed to the terminal for Accessibility and will say it has no permission while the app itself is trusted. [docs/testing.md](testing.md#seeing-what-auto-measured) has the output and how to read it, and [docs/permissions.md](permissions.md) says the rest in short.

**Automation, only for the jump to a terminal.** A click on a row of the panel's Sessions card brings that session's terminal tab forward, from what the session's own hook read in its environment (never a window title): Warp by its focus link, kitty, WezTerm and tmux by their own command-line tools, and iTerm2, Terminal and Ghostty by one Apple event each, which is the one thing that asks a permission — macOS's own *control "iTerm2"* dialog, once per app, the first time, never at launch. Settings › Assistants › Sessions shows where each grant stands and opens the Automation pane; the click is off with one switch, and nothing is ever launched that is not already running ([docs/permissions.md](permissions.md#automation-only-for-the-jump-to-a-terminal)).

**Where it sends things.** Each token goes only to the vendor that issued it, over HTTPS, in the same read-only status requests that vendor's own app or dashboard makes: `api.anthropic.com/api/oauth/usage`; `chatgpt.com/backend-api/wham/usage` (and, only if you opt in, `/wham/rate-limit-reset-credits`); `cursor.com/api/usage-summary`, `/api/dashboard/get-current-period-usage` and `/api/dashboard/get-sand-usage-status` (and, while *Also read Cursor's usage events* is on, which it is unless you turn it off, `/api/dashboard/teams` for the team id and `/api/dashboard/get-filtered-usage-events` for the last 30 days of events); `api.github.com/copilot_internal/user` (and, only if you opt in, `/user/orgs` and `/orgs/<org>/settings/billing/usage/summary`); and for Google the calls Gemini CLI and Antigravity make at every start, `v1internal:loadCodeAssist`, `:retrieveUserQuotaSummary` and `:retrieveUserQuota`, on `daily-cloudcode-pa.googleapis.com` and `cloudcode-pa.googleapis.com` (the host Antigravity's own log names, else both in that order until one answers with a live figure). Every request names itself with a `User-Agent: Notchmeter/<version>` header, with two exceptions, stated here because those two endpoints answer only the vendor's own client: the Copilot quota read (`copilot_internal/user`) carries `User-Agent: GitHubCopilotChat/0.26.7`, `Editor-Version: vscode/1.96.2`, `Editor-Plugin-Version: copilot-chat/0.26.7` and `X-Github-Api-Version: 2025-04-01`, the headers the Copilot Chat extension sends, and every Code Assist call made with an Antigravity login (the Antigravity app, its home folder or its CLI's folder is on this Mac) carries `User-Agent: antigravity` and a `Client-Metadata` header naming the Antigravity IDE, while a Gemini CLI login keeps the Notchmeter header. Those requests are made under those clients' own identity and are still the same read-only reads with the same token; the values are constants in [`CopilotProvider.swift`](../Sources/Notchmeter/CopilotProvider.swift) and [`AntigravityProvider.swift`](../Sources/Notchmeter/AntigravityProvider.swift), and [docs/accuracy.md](accuracy.md) says why each is needed. Requests follow the proxy in Network settings, or the one you set in Settings › Advanced. The one other request is the update check: Sparkle fetches `https://github.com/Amir-Hackett/notchmeter/releases/latest/download/appcast.xml` (the `SUFeedURL` in [`scripts/Info.plist`](../scripts/Info.plist)) from GitHub once a day, at most, and when you press *Check for Updates…*. It is a plain GET carrying Sparkle's default `User-Agent: Notchmeter/<version> Sparkle/<version>` and nothing else: no token, no usage figure, and no system profile (`SUEnableSystemProfiling` is not set, so Sparkle's anonymous profile is never sent). An update is downloaded from the same GitHub release only when one is offered and you accept it, or when you have turned on *Download updates automatically*, which is off unless you do. Settings › Updates › *Check for updates automatically* turns the daily check off, and a build you compile yourself never checks at all ([`Updater.swift`](../Sources/Notchmeter/Updater.swift)). Nothing is sent anywhere else. There is no telemetry, no analytics, no crash reporting and no server of ours. The optional local API answers on 127.0.0.1 only, to processes on this Mac, and is off by default; a vendor's Usage or Status link in a card opens that vendor's page in your browser and nothing else.

**What it keeps.** No token is copied anywhere lasting, logged, or printed; `--probe` and the unified log show parsed numbers only. What is persisted: your settings, the last good reading per tool and which notifications have been sent in this app's own preferences; quarter-hour totals per transcript in `~/Library/Caches/Notchmeter/` so relaunches are instant, with the entry-level detail behind them kept only for the transcripts of the current 5-hour block, the daily-totals file `~/Library/Application Support/Notchmeter/daily-history-v1.jsonl` (day, cost, token counts, per-model and per-project cost) that outlives transcript cleanup, with an empty `daily-history-v1.jsonl.lock` beside it that serialises the app's and the command-line tool's writes — builds before 0.5.0 kept that file in Caches, and a copy left there is merged into the new one and removed by the first process that touches the history after the upgrade; the drain log `~/Library/Application Support/Notchmeter/drain-log-v1.jsonl` (time, tool, window, used fraction, reset, and each extra-usage rise with the plan windows at the time); and the report file `~/Library/Application Support/Notchmeter/report-v1.json` beside it, the `--probe --json` document with the app's pid, rewritten every 30 seconds while the app runs so the command-line tool and the status line can read it. With Debug logging on, each vendor request's status code and size go to the unified log. Those hold timestamps, model names, token counts, message ids, project folder names and the inference-geography flag, never prompt or response text and never a token. Reset All Settings clears the preferences and relaunches; the caches, the history and the log stay. The Homebrew cask's `zap` names every one of these paths.

**What it never does.** It never signs in, never refreshes a token, never opens a login page, and never makes an inference request, so it consumes no model capacity and cannot change the usage it reports. Each reading is borrowed from a tool you are already signed in to; sign out of that tool and the reading goes with it.

**How often.** The base cadence is every 5 minutes for every tool (Claude, Codex, Cursor, Antigravity, Copilot), and the local cost scan every minute (it only re-reads files that changed). Claude and Codex were 3 and 2 minutes until September 2026; they were raised to 5 because a 2–3 minute poll against a first-party endpoint from an unofficial client is the behaviour that gets noticed, and the hook, the status line and the hover refresh give freshness where it matters (a turn ending refreshes at once; while the status line reports, the Claude endpoint is read only on Refresh, at the reset of a window the status line does not carry, and at most every 30 minutes for those windows). The schedule adapts, by the rules in [`PollingPolicy.swift`](../Sources/Notchmeter/PollingPolicy.swift): nothing at all while the screen is locked, the displays are asleep or the Mac is asleep; every 15 minutes while another macOS user's session is in front, which slows the reading rather than stopping it, because a switched-out session's agents go on running and the limits belong to an account rather than to a Mac; half as often on battery or in Low Power Mode; a quarter as often once a tool's files on disk have not changed for 30 minutes, which is checked once a minute with a few directory listings (Claude Code's three most recently changed project folders in each transcript root, Codex's rollouts for today and yesterday, the modification time of Cursor's state database, Gemini CLI's login file and its per-project and Antigravity folders, Copilot's config folder); never more than 15 minutes apart while awake, and never faster than the base cadence. Unlocking or waking reads everything at once (a few seconds after a wake, so the network is back first), a Claude Code hook event refreshes Claude at most once every 30 seconds, hovering the panel refreshes a tool at most once a minute, the footer's "Next update in…" line and ⌘R refresh everything now and a card's context menu refreshes one tool, a rate-limit answer backs off for at least a minute, and other failures back off from 30 seconds up to 10 minutes. A transport failure (no network, DNS down, a timeout) is not an error: the cached reading stays without a problem mark and the footer says "Offline, retrying". The panel footer always shows the real next read and why it is later than usual ("no agent activity", "on battery", "low power mode", "another user is logged in").

**Terms.** Each vendor's terms are written for its own apps and restrict automated access to its services in broad language, and none of them names the one thing Notchmeter does: a read-only status request, made with the login that vendor's own tool keeps on this Mac, to the endpoint that tool itself reads. Anthropic's are the most specific, so they are quoted here rather than summarised. Claude Code's [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) page, under *Authentication and credential use* (read 2026-09-20): "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." And: "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The [Consumer Terms of Service](https://www.anthropic.com/legal/consumer-terms) (effective October 8, 2025), section 3, *Use of our Services*: "You may not access or use, or help another person to access or use, our Services in the following ways: […] 4. To crawl, scrape, or otherwise harvest data or information from our Services other than as permitted under these Terms. […] 7. Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise."

Notchmeter's reading of those, stated so that you can disagree with it: it offers no login and never opens one (signing in happens in Claude Code, through Anthropic's own flow, or not at all); it routes nothing (no request of yours, and no inference request of its own, ever goes through the token); it collects, stores and intermediates no credential (the token Claude Code saved is read into memory for one request and never written, logged, printed or passed on); every request to Anthropic names itself with a `User-Agent: Notchmeter/<version>` header, so nothing is disguised; and the endpoint it reads is the one named under *Where it sends things* above, asked at most every five minutes and not at all while a session is running. That poll is still a script making a request, which is what item 7 describes, and the app does not pretend otherwise. The channel Anthropic documents is the [status line](hooks.md#the-status-line), which hands the same session and weekly figures to a command of your choosing with no network at all; with it installed the endpoint is not asked while a session runs, and Settings › Assistants › Claude Code has *Also poll Claude's usage endpoint*, off which the status line is the only Claude source and Notchmeter makes no request to Anthropic whatever. That switch is also the fallback should Anthropic answer the inquiry with a no. Whether to run it under your account is your decision. The other four vendors get the same path and the same reading, with the two exceptions *Where it sends things* states: the Copilot quota read and Antigravity's Code Assist calls are made under those clients' own identity, because those endpoints answer no other, and that is said there rather than left for you to find in the code. If a vendor withdraws its usage endpoint, the meter reports the error and waits; it does not look for another way in. In particular it never probes Anthropic's inference endpoint for the rate-limit headers other meters read, because that is an inference call; the reasoning is in [docs/accuracy.md](accuracy.md#why-there-is-no-header-fallback).
