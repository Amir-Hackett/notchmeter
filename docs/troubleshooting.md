# Troubleshooting

```bash
/usr/bin/log show --last 10m --info --predicate 'subsystem == "com.amirhackett.notchmeter"' --style compact
```

- *Claude: needs your permission* — every silent route to the login failed (the Keychain with prompts off, `security find-generic-password`, the credential files, `CLAUDE_CODE_OAUTH_TOKEN`); *Ask for Keychain access* in Settings, or ⌘R, asks once while *Ask for Keychain access* (Settings › Advanced › Privacy) is *Only on refresh*.
- *Claude Code is on an API key: no plan windows to meter* — an `ANTHROPIC_API_KEY`, Bedrock, Vertex or `apiKeyHelper` setup has no usage window to read; the Cost card is the meter.
- *Claude: Not updated since …* — Claude Code renews its login only when `claude` runs in that Mac account, so in an account where it is rarely run the login goes idle. Run `claude` there once and the notch picks it up within a minute. Notchmeter never renews it itself: a renewal from here rotates the refresh token and could sign Claude Code out. Since 0.9.9 this is one grey line under the kept reading rather than an orange warning, because nothing is wrong.
- *Codex: login was refused / expired* — run Codex once; it signs back in and the notch picks it up.
- *Codex: Session — No data* — the plan publishes no 5-hour window (free plans get a monthly one).
- *Cursor: plan has nothing to meter* — free plans publish no included-usage limit; the ring appears once a paid plan does. An Enterprise seat billed on-demand says the same and reads 0 % on Cursor models and All models however much it spends: pick *Today's spend* as the outer ring in Settings › Assistants › Cursor (it needs *Also read Cursor's usage events*, on by default).
- *Gemini: Sign in to Gemini CLI* — the meter uses the Google login Gemini CLI caches in `~/.gemini/oauth_creds.json`; run `gemini` once and choose Login with Google. An API-key or Vertex AI setup has no quota to read.
- *Antigravity keeps its own login in the Keychain* — the Antigravity row reads the same Gemini CLI login, under Antigravity's identity, because the app's own is not on disk; sign in to Gemini CLI with the account you use in Antigravity.
- *Gemini or Antigravity: login has expired / was refused* — run Gemini CLI (or Antigravity) once; it signs back in and the notch picks it up.
- *Gemini: Google stopped serving Gemini CLI quota to personal accounts* — since June 2026 the endpoint answers only Code Assist Standard and Enterprise accounts under Gemini CLI's identity; nothing on this side can change that. The Antigravity row asks under Antigravity's identity and can still have figures; switch the Gemini row off in Settings › Assistants if you only use Antigravity.
- *A Gemini row appeared after updating to 0.9.0* — Gemini CLI and Antigravity used to share one row; they are two now, and the new Gemini row took over the old row's settings. A Mac with only Gemini CLI shows only the Gemini row.
- *Kimi: login has expired* — Kimi Code refreshes its short-lived token only while it runs, and Notchmeter never refreshes it; run `kimi` once and the notch picks it up. The last reading stays on screen meanwhile.
- *Kimi: Sign in to Kimi Code* — run `kimi`, then `/login`; the meter needs the login the CLI keeps in `~/.kimi/credentials`.
- *Kimi: the usage endpoint answers only a Kimi Code membership* — the account behind the login is not on a Kimi Code plan (the endpoint answers 404), so there is no allowance to meter.
- *Kimi: a window with no figure* — Moonshot publishes no plan sizes, so a window the answer gives no limit or ratio for is shown without one rather than as empty or full.
- *Cost card says "Pricing local files"* — the first scan of a large `~/.claude/projects` takes a few seconds; later scans only read files that changed.
- *Footer says "Next update in 12m · no agent activity"* — nothing of the tool's has changed on disk for 30 minutes, so the meter polls a quarter as often; start a session (or install the assistant's hook) and it returns to the base cadence within a minute. "Paused while the screen is locked" clears on unlock.
- *Two macOS accounts, and one of them shows older figures* — every login has its own copy of everything: its own `~/Library/Application Support/Notchmeter/`, drain log, settings, Keychain and vendor logins. Two profiles can therefore be signed into different Claude or Cursor accounts and read entirely different numbers, and neither can see the other's files (`~/Library` is `0700`). `/Applications` is shared, so both run the same copy of the app, but installing a new one only reaches a session when that session's instance is relaunched — `scripts/build.sh install` quits and reopens the app for the account running it and cannot touch the other, so quit and reopen Notchmeter on the other account too. While a session is switched out its meter reads every 15 minutes rather than stopping, and the footer says "another user is logged in".
- *The hook badge never appears* — Settings › Integrations › Hooks shows, per assistant, whether the entry is installed and whether it points at the running copy, and its button opens that assistant's page, where "Installed but points at an old path" and "Installed, but an entry is out of date" have a Repair button; on the same page, check that *Read its sessions* is on, since with it off the assistant's events refresh its meter and nothing else; then see the checks at the end of [docs/hooks.md](hooks.md).
- *The Cursor ring shows the tick but never the waiting dot* — by design: Cursor has no hook event for a wait on your approval, a permission mode or a rate limit, so its ring asserts only what its events prove ([docs/hooks.md](hooks.md#cursor), "What Cursor does not report"). Turn on *Require notch approval for every command* or *Mirror Cursor's cards* in Settings › Cursor to get a real wait.
- *Cursor's Run or mode-switch card is on screen but not in the notch* — *Mirror Cursor's cards* needs the Accessibility permission (System Settings › Privacy & Security › Accessibility › Notchmeter) and a Cursor chat the hook has reported as in a turn; a card is looked for only during one. A plan's card is not mirrored as a card: its buttons are the row's own **View Plan** and **Build**. A Cursor update can rename a card's buttons; the card then stays in Cursor alone. The diagnostics report's `cursor:` line shows which capabilities are live.
- *Cursor's status bar says Screen Reader Optimized* — *Mirror Cursor's cards* is on: reading Cursor's cards means asking Cursor for its accessibility tree, and Cursor takes that for a screen reader. Set `"editor.accessibilitySupport": "off"` in Cursor's settings to keep the editor as it was, or turn the switch off, which tells Cursor the app has stopped reading.
- *Cursor's question shows on the notch with no choices to press* — since 0.9.20 a question's choices are buttons wherever Cursor's window is, with Cursor's own **Skip** and **Continue** under them: the question is read from Cursor's own database, picked on the notch, and put on Cursor's own card when you press Continue. (0.9.19 offered the buttons only where it could read the whole card out of Cursor's window, and for a question with a file's name or a word in bold in it, it could not.) Three things still leave a question with its words and **Answer in Cursor** alone. *Show what a session is working on* is off, or the screen is shared: a question's words are hidden then, and Continue is not offered on a question that cannot be read. *Mirror Cursor's cards* has no Accessibility permission, which is what Cursor's card is pressed with. Or an answer could not be put on Cursor's card, which the row says, below; that question is answered in Cursor from then on. The choice that is typed (*Other...*) is always answered in Cursor.
- *Cursor asked a question while its window was minimised, or Cursor was hidden, and the notch said nothing* — before 0.9.19 it could not: Cursor does not draw a window that is put away, so there was no card to read until the window came back. Since 0.9.19, with *Mirror Cursor's cards* on, the question is also read from Cursor's own database, and reaches the notch within a few seconds wherever the window is. Since 0.9.20 it is answered there too, and Cursor is not brought forward for it. Other prompts of Cursor's (Run, a mode switch) are read from the window alone. From a window that is merely behind another they reach the notch as they do from one in view, and are pressed where the window is: Cursor keeps a covered window readable. From a minimised window, or a hidden Cursor, they may not be there to read. Since 0.9.20, while a Cursor chat in a turn has said nothing for two seconds, Cursor is asked once a second to bring its windows up to date; whether that brings a minimised window's card has not been confirmed, and where it does not, the prompt arrives as *Cursor may be waiting* once the chat has been quiet for the time set by *Call a quiet Cursor turn a possible wait after* in Settings.
- *I picked a choice on the notch and nothing was sent* — a pick is not an answer, in the notch or in Cursor: press **Continue** under the choices to send it. On a card with several questions Continue stays dimmed until each has a choice picked, as Cursor's own does nothing before then. On a question with one answer, pressing the picked choice again unpicks it, as it does in Cursor.
- *The row says "Could not reach this question in Cursor's window; answer it in Cursor"* — the answer was not sent. Continue found no card for the question in any Cursor window it could read, in six reads with Cursor asked to bring its windows up to date between them. The usual reasons: the chat that asked is not the one its window is showing (another chat's tab is in front in that window); Cursor's question card is minimised to its header; the window is on another Space or full screen elsewhere, which macOS does not let another app read; the window is minimised, or Cursor hidden, and Cursor did not bring its contents up to date when asked; Cursor was first asked for its window's contents when the window was already out of sight, and has none to give until the window is next drawn; or the question was asked in Cursor's Agents window, which draws its question card another way that the notch does not press yet. **Answer in Cursor** takes you to it. *Cursor would not take the press; answer it in Cursor* is the other case: the card was found, and either it does not say which choices are picked or a press on it did not show.
- *The row says "Another chat is asking the same question; answer it in Cursor"* — two Cursor chats are waiting on the same question, or on two that differ by a word, over the same choices and in workspaces of the same name, which is what the same prompt run in two worktrees of one repository gives. Cursor's windows do not say which of the two cards belongs to which chat, and an answer sent to the wrong one cannot be taken back, so the notch sends nothing. Answer one of them in Cursor; the other can then be sent from the notch.
- *A Cursor subagent has a row of its own on the Sessions card* — before 0.9.21 every subagent did: Cursor runs one as a chat of its own, and its events name that chat alone. Since 0.9.21 the app reads from Cursor's state database which chat a new conversation works for, and a subagent's work is on its conversation's row, under the subagent line it already had. A row can still appear for one where Cursor's database could not say: it could not be read, or it held nothing of the chat, which is waited out for a second and three quarters while a subagent is known to be running. Such a row goes as the subagent ends, where Cursor's `subagentStop` names the chat it ran as (3.23.23 does when it knows it). The log says each time a chat was placed, and, while a subagent was running, each time one was not: `log show --last 10m --predicate 'subsystem == "com.amirhackett.notchmeter"' | grep "cursor chat"`. A Cursor on another machine that reports through the local API has rows for its subagents as before ([docs/hooks.md](hooks.md#cursor), *A subagent's own chat*).
- *A Cursor row is idle while its subagent is still working* — the subagent was left running after the conversation's own turn ended. Its work moves the row's clock and nothing else: the subagent line goes with the turn, and the row is working again when the conversation itself next speaks.
- *A Cursor chat says* May be stuck — five commands failed in a row, with no command working and no edit landing between them ([docs/hooks.md](hooks.md#may-be-stuck)). Cursor does not report a read or a search that worked, so those between the failures do not end the run, and a command that only reports through its exit status (`grep` finding nothing, `test`, `which`) is a failure to Cursor, so a run of those reads the same. The flag goes when a command works, an edit lands or the turn ends, is off the row while the chat waits for you, and lapses once the last failure is ten minutes old.
- *A card showed on the wrong Cursor row* — with several Cursor chats in a turn at once in the Agents window, whose title names no workspace, the card goes to the chat its header names, which the app learns from Cursor's own chat names, else to the chat heard from last. That last case is a chat Cursor has not named yet (it names one after its first reply), or *Show what a session is working on* off, or the screen being shared, since chat names are not read then. The press still goes to the card itself, whichever row shows it.
- *Every Cursor command now waits for the notch* — that is *Require notch approval for every command*. Turn it off in Settings › Cursor; an unanswered call falls back to Cursor's own prompt, never to running.
- *The Codex row says installed but nothing arrives* — open `/hooks` inside Codex and trust the entry: Codex skips a new or changed hook until you do, and a session already running keeps the hooks it started with. A Repair (a moved app) changes the entry and needs trusting again ([docs/hooks.md](hooks.md#codex)).
- *The Gemini CLI, Copilot or Kimi Code row says installed but nothing arrives* — each reads its hook file when it starts: open a new Gemini or Kimi session, or restart Copilot CLI and check `/env` lists `notchmeter.json` ([docs/hooks.md](hooks.md#gemini-cli), [Copilot](hooks.md#github-copilot-cli), [Kimi Code](hooks.md#kimi-code)).
- *The Gemini CLI hook row says an entry is out of date after updating to 0.9.0* — the entry still names the old combined row (`--tool antigravity`); it keeps working, and Repair (or the launch repair) rewrites it to `--tool gemini`.
- *Kimi Code: Add says config.toml already defines hooks in another form* — the file has a `hooks = [...]` array or a `[hooks]` table, which an appended `[[hooks]]` table would break; it is left untouched, so paste the snippet in by hand ([docs/hooks.md](hooks.md#kimi-code)).
- *The Kimi ring shows the tick but never the waiting dot* — by design: Kimi Code has no permission event, and its notifications are background-task notices, not waits on you.
- *The Antigravity ring never reacts to the Antigravity IDE* — by design: only Gemini CLI documents the events the notch needs (a session, a prompt, the end of a turn, a wait), and the IDE's own hooks file documents none of them, so Antigravity has no hook; Gemini CLI's hook lights Gemini CLI's own ring ([docs/hooks.md](hooks.md#gemini-cli), "The Antigravity IDE").
- *Copilot: Sign in to GitHub Copilot* — the meter needs the token Copilot's editor plugin or `gh auth login` saves; a Copilot subscription without either on this Mac has nothing to read.
- *Footer says "Offline, retrying"* — the network is down or the host unreachable; the last reading stays on screen without a problem mark until it is back.
- *Nothing on screen on a Mac without a notch* — the top layout is a pill under the menu bar there, and the menu bar icon is on by default so Settings and Quit are always reachable.
